# 加入一篇筆記

使用者會貼上一段筆記（多半是舊的 HackMD 內容），要求整理進這個公開的 GitHub notes 倉庫。依下列步驟處理。

## 1. 判斷獨立成篇還是併入既有篇

先看 `README.md` 列出的既有篇目，判斷主題重疊程度：

- **完全重疊或只是同主題的延伸**（例如都是 ESLint/Prettier、都是 QGIS 道路查詢）→ 併入既有篇，加一個新章節，不要開新檔案。
- **同工具但不同面向**（例如已有 Linux 的 SSH，現在來 Windows 的 SSH）→ 另開一篇，兩篇互相在開頭連結。
- **全新主題** → 新開檔案，檔名用小寫 kebab-case，內容需要細分時用 `topic-subtopic.md`（例如 `ssh-linux.md`、`ssh-windows.md`）。

不確定時，用 `Read`/`Grep` 掃過候選的既有檔案再決定，不要只憑檔名猜。

## 2. 事實查核，不要照抄

原始筆記常常是舊的、有錯字、版本過時，或路徑/指令已不適用。**逐項核對後才寫進文件**：

- 指令、套件名稱、API 用法：能查證的就用 `Bash`/`Grep`/`WebFetch` 核對現況（例如版本是否還在維護、指令是否已改名）。
- 如果 notes 倉庫旁邊有相關專案原始碼（例如 `~/source/web_server`），優先用專案的實際設定檔、`package.json`、entity 定義等驗證，而不是憑印象。
- 找到的錯誤要修正並在回覆裡列出改了什麼、為什麼改，不要默默改掉不說。
- 明顯過時或已知有更好做法的（例如某工具已停止維護），標註並給替代方案，不要整段刪除也不要照單全收。

## 3. 套用倉庫既有格式慣例

打開任兩篇既有筆記對照，統一遵守：

- 標題：`# 篇名`，簡短，不要加解釋性副標。
- 開頭一段 `>` 引言，一到兩句說明這篇在講什麼。
- 有分節的話一定要有「## 目錄」，每個章節連到 `#anchor-id`。
- 每個 `## 章節` 前面放 `<a id="anchor-id"></a>`，anchor 用小寫英文與連字號。
- 章節之間用 `---` 分隔。
- 章節標題習慣加一個表意的 emoji（不強制但保持一致）。
- 需要勾選的清單（例如擴充套件清單、安裝清單）用 HackMD 相容的 task list 語法：`- [x] 項目` / `- [ ] 項目`，不要用表格，因為表格在 HackMD 裡無法打勾。
- 表格只用在真正是「多欄對照」的資料，不要把清單硬塞進表格。
- 每篇結尾放「## 📚 參考資料」，列出外部連結。
- 純資訊性的補充用 `> 說明文字`，警告用 `> ⚠️ **重點**：說明`。

## 4. 圖片規則（重要，容易出錯）

- 圖片一律存到 `images/` 目錄，檔名用 `<篇名>-<用途>.png` 這種可讀命名，不要保留 HackMD 或 Windows 產生的亂碼檔名（`upload_xxxx.png`）。
- 從 Windows 複製過來的圖檔常帶 `<檔名>:Zone.Identifier` 附屬檔，清掉它，不要進版控。
- **圖片一律用絕對網址引用，不要用相對路徑 `images/xxx.png`。** 格式：
  `https://raw.githubusercontent.com/kevin6655111/notes/main/images/<檔名>.png`
  原因：這些筆記會被貼到 HackMD 檢視，HackMD 沒有倉庫路徑的概念，相對路徑在那裡一定是破圖；絕對網址則是 GitHub、HackMD、VS Code 本機預覽三邊都能顯示。
- 用絕對網址代表**圖片必須先 commit 且 push 過**才看得到，沒 push 之前先用相對路徑草稿，完成後如果使用者確認要 commit，記得改回絕對網址並確認遠端能抓到（可用 `curl -sS -o /dev/null -w '%{http_code}' <url>` 驗證回 200）。
- 不確定某張圖對應筆記的哪一段時，先用 `Read` 工具把圖讀出來看內容，不要用檔名猜。
- 原始筆記裡的外部圖床連結（hackmd.io/_uploads/... 之類）如果已經 404，直接移除，不要留著死連結或誤導性的註解。

## 5. 敏感資料檢查（這是公開倉庫）

在寫入任何內容前後都要掃一次：

- 真實對外 IP（非 `10.`/`172.16-31.`/`192.168.`/`127.0.0.1` 等私有網段，也非 `203.0.113.x`/`198.51.100.x` 這類 RFC 5737 文件保留網段）→ 換成保留網段或移除。
- 明文密碼、API key、授權序號、token → 一律不寫入，改成「去哪裡找」的說明（密碼管理器、公司系統），並在 mount/連線類指令裡示範用 credentials 檔取代明文密碼寫在指令列。
- 同事姓名與其個人能力清單、私人聯絡方式 → 不收錄，除非使用者明確確認這些人同意公開。
- 使用者自己的帳號名稱寫死在指令裡（例如 `chown -R kevin:kevin`）→ 改成 `$USER` 之類的通用寫法。

抓到問題不要默默處理，在回覆裡明講移除或修改了什麼、為什麼。

## 6. 更新 README 與交叉連結

- 新篇一定要加進 `README.md` 的清單，連結文字用篇名。
- 找既有篇目裡主題相關的段落，加一句話互相連結（例如格式化筆記裡提到換行字元就連到 EOL 那篇），但不要為了連結而連結。
- 篇名如果太長，優先縮短成關鍵詞（使用者常會要求「標題太長」），不要塞副標在標題裡。

## 7. 收尾驗證

寫完後跑一次檢查，不要跳過：

```shell
python3 -c "
import re,os,glob
for f in sorted(glob.glob('*.md')):
    s=open(f,encoding='utf-8').read()
    toc=set(re.findall(r'\]\(#([\w-]+)\)',s))
    anc=set(re.findall(r'<a id=\"([\w-]+)\">',s))
    if toc-anc: print(f, '壞錨點', toc-anc)
    if s.count('\`\`\`')%2: print(f, '程式碼區塊不成對')
    if not s.endswith('\n'): print(f, '缺檔尾換行')
"
```

- 目錄裡每個連結都要有對應的 `<a id="...">`。
- 程式碼區塊要成對（不能被中途截斷）。
- 檔尾要有換行。
- 跨檔連結（`[文字](other.md)`）維持相對路徑即可，不用改成絕對網址——GitHub 上能點，HackMD 上雖點不動但連結文字本身已經寫明是哪篇筆記，讀者看得懂。
- README 的清單與實際檔案是否一致（每個 `.md` 都有列出、沒有列出不存在的檔案）。

## 8. 何時要停下來問

- 使用者給的內容明顯需要移除大量段落或整篇拿掉時，先做完能做的部分，把「建議移除但尚未確認」的部分明講出來，等使用者回應，不要自己決定砍掉一大段。
- 涉及是否要保留同事個資、公司內部網路資訊這類會影響隱私或安全的判斷，寧可保守也要在回覆裡點出來讓使用者決定。
- 除此之外（合併或獨立成篇、圖片檔名、章節怎麼分、標題怎麼縮短）都可以自行判斷後直接做，不用每件小事都問。

## 9. Git

除非使用者明確要求 commit，否則只修改工作目錄，不要自己 commit 或 push。commit message 若被要求，遵循使用者專案既有的 `類型: 主題(#編號)` 慣例（觀察 `git log --oneline -5` 抓格式），不要自己發明新格式。
